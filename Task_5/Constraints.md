# Task 5. Constraints, Formalisation and Violations (Railway Crossing)

## 5.1 Variables

Train_Present (a train is approaching or in the crossing zone), Barrier_Open, Barrier_Closed (= ¬Barrier_Open), Barrier_Open_Cmd, Crossing_Clear (confirmed clear by the safety-monitoring unit), Alarm_On, Lights_On, Robot_Entering_Crossing, Train_Sensor_OK, Barrier_Fault, ARLCCS_Link_OK, Readings_Inconsistent (sensors disagree or out of plausible range), Operator_Alert, Robot_Speed, Robot_State, Door_Open, Handover_Authorised, Chamber_Safe, Protection_Active, Batch_Removal_Allowed, Silent_Time (seconds since last heartbeat), Temp_Critical, Battery_Emergency, Elapsed (seconds since trigger), Command_Executed, Authenticated, Role_Authorised, Main_Power_Lost, Backup_Available, Incident_Recorded, Safe_Shutdown, Prev_State, At_Destination.

## 5.2 Constraints, formalisation, violation scenarios, detection and response

| ID | Constraint in simple English and why it is necessary | Formalisation | Violation scenario | Detection | Expected response |
|---|---|---|---|---|---|
| C-01 | A closed barrier must be maintained whenever a train is present, because an open barrier lets vehicles into a train's path. | Train_Present → ¬Barrier_Open | Train_Present = TRUE, Barrier_Open = TRUE | Safety monitor compares sensor and barrier-position every cycle (below 100 ms) | Close barrier, sound alarm, robot stop, operator alert, log event |
| C-02 | Warning lights and alarm must be active while a train is present, so road users know to stay out. | Train_Present → Alarm_On ∧ Lights_On | Train_Present = TRUE, Alarm_On = FALSE, Lights_On = TRUE | Monitor checks output feedback of alarm and lights | Re-trigger alarm, close barrier, operator alert, log |
| C-03 | The barrier may only be commanded open once the crossing is confirmed clear, to avoid trapping a vehicle or opening on a second train. | Barrier_Open_Cmd → Crossing_Clear | Barrier_Open_Cmd = TRUE, Crossing_Clear = FALSE | Command interlock checks the clearance flag before the command | Block the command, keep barrier closed, alarm stays on, log |
| C-04 | The robot must not enter the crossing unless the barrier is open and no train is approaching, as it cannot withstand a train collision. | Robot_Entering_Crossing → Barrier_Open ∧ ¬Train_Present | Robot_Entering_Crossing = TRUE, Barrier_Open = FALSE, Train_Present = TRUE | Robot reads the ARLCCS status before the stop line and the monitor compares it with robot position | Robot emergency stop at the stop line, operator alert, log; Safe Mode if already inside |
| C-05 | If the train-detection sensor fails, the system must fail safe by closing the barrier, because absence of a signal does not mean no train. | ¬Train_Sensor_OK → Barrier_Closed ∧ Operator_Alert | Train_Sensor_OK = FALSE, Barrier_Closed = FALSE, Operator_Alert = FALSE | Sensor self-test and heartbeat timeout in the monitoring unit | Close barrier, alarm on, robot waits outside, operator alert, log |
| C-06 | A faulty barrier means the crossing cannot be trusted, so the robot must not enter and the operator must be told. | Barrier_Fault → ¬Robot_Entering_Crossing ∧ Operator_Alert | Barrier_Fault = TRUE, Robot_Entering_Crossing = TRUE | Position feedback does not match command within 2 s | Robot stops, operator alert, event logged, maintenance requested |
| C-07 | If communication with the ARLCCS is lost, the robot must assume it is unsafe, since its barrier information is stale. | ¬ARLCCS_Link_OK → ¬Robot_Entering_Crossing | ARLCCS_Link_OK = FALSE, Robot_Entering_Crossing = TRUE | Missing ARLCCS heartbeat for 2 s | Robot stops 5 m before crossing, operator alert, log; Safe Mode if inside |
| C-08 | Inconsistent or implausible sensor readings must be treated as a train being present (conservative assumption). | Readings_Inconsistent → Barrier_Closed ∧ Alarm_On | Readings_Inconsistent = TRUE (one sensor says Train_Present = TRUE, the other FALSE), Barrier_Closed = FALSE | Cross-check between redundant sensors and range checks | Assume train, close barrier, alarm, operator alert, log |
| C-09 | The robot must never move while the chamber door is open, because the batch would be exposed and the door could be damaged. | Robot_Speed > 0 → ¬Door_Open | Robot_Speed = 1.2 m/s, Door_Open = TRUE | Door sensor monitored together with the drive controller | Immediate stop, chamber enters CH-SUSPENDED, operator alert, log |
| C-10 | While the robot is DELIVERING with the door open, it must be stationary and the handover must be authorised, so only the intended clinic can access the batch. | Robot_State = DELIVERING ∧ Door_Open → Robot_Speed = 0 ∧ Handover_Authorised | Robot_State = DELIVERING, Door_Open = TRUE, Handover_Authorised = FALSE | Door lock controller checks authorisation | Re-lock door, alert operator, log; Safe Mode if the door cannot be closed |
| C-11 | A batch may only be removed when the chamber is safe and no protection response is active, to avoid removing an unsafe batch or interrupting protection. | Batch_Removal_Allowed → Chamber_Safe ∧ ¬Protection_Active | Batch_Removal_Allowed = TRUE, Protection_Active = TRUE | Lock controller reads the chamber state | Keep door locked, refuse removal, alert, log |
| C-12 | If there is no heartbeat for more than 15 s, the robot must be in LINK_LOST or SAFE_MODE, because it cannot be supervised. | Silent_Time > 15 → Robot_State = LINK_LOST ∨ Robot_State = SAFE_MODE | Silent_Time = 20, Robot_State = NAVIGATING | Heartbeat watchdog on the robot | Enter LINK_LOST, halt at safe point, buffer log, Safe Mode after 300 s |
| C-13 | A command may only be executed if the operator is authenticated and role-authorised (CR-03). | Command_Executed → Authenticated ∧ Role_Authorised | Command_Executed = TRUE, Authenticated = TRUE, Role_Authorised = FALSE | Execution log audited against the authorisation check | Reject, undo if possible, security alert, log |
| C-14 | Critical temperature or emergency battery must put the robot in Safe Mode within 3 s (CR-01). | (Temp_Critical ∨ Battery_Emergency) ∧ Elapsed > 3 → Robot_State = SAFE_MODE | Temp_Critical = TRUE, Elapsed = 5, Robot_State = NAVIGATING | Monitor compares trigger timestamp with state change | Force SAFE_MODE, operator alert, log as a timing defect |
| C-15 | DELIVERING may only be entered from NAVIGATING at the destination, never from IDLE or AVOIDING_OBSTACLE. | Robot_State = DELIVERING → Prev_State = NAVIGATING ∧ At_Destination | Robot_State = DELIVERING, Prev_State = IDLE, At_Destination = FALSE | State-machine guard and runtime monitor on transitions | Reject transition, stay in previous state, log, operator alert |
| C-16 | On power loss with no backup, the incident must be recorded and the chamber must shut down safely. | Main_Power_Lost ∧ ¬Backup_Available → Incident_Recorded ∧ Safe_Shutdown | Main_Power_Lost = TRUE, Backup_Available = FALSE, Incident_Recorded = FALSE | Power-fail interrupt, then a capacitor-backed log write | Write incident, safe shutdown within 5 s, operator alert |

## 5.3 Coverage check against the task requirements

- At least 10 constraints: 16 (C-01 to C-16).
- At least 8 formalised with ∧, ∨, ¬, → and 8 violation scenarios: all 16.
- Robot-chamber links: C-09 and C-10 (also C-11 and C-14).
- Sensor failure or communication loss: C-05, C-07, C-08 and C-12.
- Every constraint uses observable variables, so a test or runtime monitor can decide from the observed values whether it holds.
